# 视频卡顿检查与界面调整

本次修改源码与本地模拟预览，尚未重新打包。既有 1.1.3 压缩包保持不变。现场人员已确认四个点位正确，本次没有改变坐标、UDP 地址或数字人动作目录，也没有向真实设备发送动作。

## 已确认的检查结果

1. 到位逻辑没有停止播放：机械到位只更新机械点位，不调用媒体暂停、停止或播放。新增回归测试确认到位前后媒体命令序号不变，播放继续，用户途中暂停也保持暂停。
2. 当前原片 `content/videos/p01.mp4` 为 2126×3840、30 帧、H.264 Main Level 5.1，时长约 141 秒，文件 405,754,749 字节，总码率约 22.97 Mbps。这是一段高分辨率竖版视频，之前被固定横框缩小；不是普通 1080p 横片。
3. 开发电脑上的本地服务支持视频 Range 请求；读取前 16 MiB 返回 206，单次约 0.35 秒（约 383 Mbps）。只证明开发机本次读取正常，不能代表现场磁盘或浏览器性能。
4. 开发电脑软件解码前 20 秒约 12.9 倍实时速度；这不是现场浏览器的解码测试，不能据此保证现场流畅。
5. 原片 MP4 索引在文件尾部，浏览器可以通过 Range 读取；可能影响首开和跳转，不能单凭这一点解释持续卡顿。

仍待现场确认：独立浏览器还是 Host 内置浏览器卡顿；声音是否连续；缓冲余量、丢帧与暂停事件。不同电脑和不同播放器使用的解码路径可能不同。目前没有证据将故障确定为“到位后停止播放”，也不能宣称已经消除现场卡顿。

## 本次修改

- 顶部仅保留校徽、中文主题和管理员入口；展项标题紧接视频，取消大块顶部留白。
- 读取视频实际尺寸决定视频框比例，竖屏最大视频高度约 51% 可视高度；横竖素材均完整显示，不裁切，也不提供视频全屏。右侧约 28% 保留给 Host 数字人，左侧镜像参数仍有效。
- 移除页面英文、底部英文、视频上的滑动说明、连接故障提示条、数字人占位文字和边框。技术错误仅在管理员面板显示；底层状态和数字人接口仍保留错误，不伪造连接成功。
- 点位从右到左，移动期间其他点位按钮置灰；播放、暂停、停止和音量继续可用。玩偶默认关闭不变。
- 媒体控制只依赖视频源、播放状态和明确的媒体命令序号，不依赖机械到位信息。重复“播放”支持浏览器原生播完后重新播放；浏览器拒绝自动播放时提供可点击的播放入口，不再静默失败。
- 修复首次直接点“播放”但尚未切换点位时的媒体登记问题，确保“暂停”可用。这不会发送机械移动命令。
- 视频预读设置为自动；播放中不同时绘制海报，也不使用透明度叠层遮罩。未压缩、覆盖或降低原片质量。

## 现场诊断方式

重新打包并更新后，在出现卡顿的现场电脑独立页面进入管理员模式（密码 2468）。播放到卡顿时，点“复制播放诊断”，将复制的完整文本发回分析。诊断仅保存当前页面最近 80 条事件，刷新后重置；不会采集 Host Token 或密码。

- 若总帧数增加、丢帧持续增加，缓冲又充足：优先排查现场浏览器解码、显卡驱动和合成负载，但单个指标不能证明具体根因。
- 若缓冲接近零且出现“等待视频数据”：优先检查现场视频读取、磁盘和浏览器缓存。
- 若日志出现“视频暂停”或“停止归零”：对照同一时间的“滑轨已到位”、请求媒体状态，判断是否由命令、原生结束或其他行为触发。
- 索引前置或另存较轻量视频可能改善启动/解码压力；是否转码和采用何种画质，待现场诊断或用户确认后处理。

丢帧统计采用浏览器的 [getVideoPlaybackQuality](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/getVideoPlaybackQuality)；它提供丢帧等指标，不会直接报告现场采用的软件或硬件解码器。
